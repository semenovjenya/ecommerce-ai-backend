# Резюме проекта AI-ECOM

## Краткое описание

AI-ECOM — это backend + Web UI система для AI-аналитики e-commerce и маркетплейсов, в текущем контексте ориентированная на Wildberries. Проект подключается к PostgreSQL с данными WB, поднимает FastAPI backend, хранит память чатов и агентских запусков в отдельном Postgres и через OpenAI Agents оркестрирует профильных аналитических агентов: продажи, финансы, маркетинг, цены и остатки.

Главная идея системы — не просто отвечать на вопросы по базе, а превращать данные маркетплейса в управляемую диагностику: что произошло, почему это произошло, какие факторы подтверждены данными, какие не подтверждены, какие действия безопасны, а какие требуют дополнительной проверки.

## Моя роль

Я отвечаю за проектирование и развитие AI-ECOM как end-to-end системы: архитектуру AI-агентов, backend, интеграцию с PostgreSQL, ETL/Airflow-контур, парсеры, Web UI-интеграцию, облачную инфраструктуру, CI/CD, безопасность доступа к данным и коммуникацию с заказчиком.

Зона ответственности включает:

- **AI architecture:** проектирование мультиагентной логики, agent routing, domain agents, диагностического оркестратора, guardrails и правил безопасных рекомендаций.
- **Backend:** FastAPI backend, WebSocket-chat, сервисы памяти, очереди agent runs, API-контракты для Web UI и Task UI.
- **Data / ETL:** PostgreSQL-слой, read-only инструменты для агентов, Airflow DAG, парсеры WB, импорт себестоимости, price AI analysis и подготовка данных для аналитики.
- **Infrastructure:** Docker/Docker Compose, Yandex Cloud, managed Airflow, managed PostgreSQL, Compute VM, Nginx, worker-процессы и browser-based parser контур.
- **Product delivery:** встречи с заказчиком, демо, согласования логики, сбор обратной связи, объяснение работы AI-системы и итерационные доработки.

## Архитектурная схема

Высокоуровневый поток системы:

```text
Wildberries data / WB API / parser sources
        -> Airflow DAG / WB parsers / price AI parser
        -> PostgreSQL analytics storage
        -> SQL transformation layer / agent-ready data
        -> FastAPI backend / read-only tools / memory services
        -> Domain AI agents: sales, marketing, price, supply, finance
        -> Diagnostic Orchestrator / safety checks / synthesis
        -> Web UI chat / action tasks / unit economics / traces
```

Логика разделена на независимые слои: Airflow отвечает за загрузку и пересчеты, PostgreSQL хранит данные и подготовленные аналитические слои, backend дает контролируемый доступ к данным, агенты выполняют диагностику, а Web UI показывает пользователю итоговый ответ, задачи и историю анализа.

## Основные части системы

- **FastAPI backend:** API для чата, WebSocket-чата, истории сообщений, трассировок агентских запусков, SKU preview, импорта себестоимости, action tasks, юнит-экономики и калькулятора комиссий.
- **Web UI:** React/Vite интерфейс из соседнего проекта `../WEB UI` с основными экранами чата, юнит-экономики и задач. UI работает через backend, использует WebSocket для чата, показывает форматированные ответы агентов, SKU preview, action tasks и встраивает отдельный Task UI через nginx-прокси.
- **Airflow ETL:** отдельный Airflow-контур в актуальном проекте `ETL WB` оркестрирует загрузки, пересчеты и AI-анализ цен. Price AI parser запускается как Airflow-пайплайн, работает по SKU и готовит данные для ценового агента.
- **AI-ядро:** `runner.py`, `main_agent.py` и `agent_queue.py` строят мультиагентный workflow: определяют домен запроса, вызывают профильного агента, добавляют смежные проверки, сохраняют ход выполнения и синтезируют финальный бизнес-ответ.
- **Доменные агенты:** sales, finance, marketing, price и supply работают по отдельным промптам и разрешенным источникам данных, чтобы не смешивать метрики и не выдумывать причинность.
- **Данные и витрины:** SQL-слой собирает представления для агентов по продажам, остаткам, маркетингу и финансам. Отдельно поддерживается импорт закупочной себестоимости для расчета маржинальности.
- **Память и трассировка:** система сохраняет чаты, summary, сообщения, action tasks, agent run traces, раунды, вопросы, ответы агентов и открытые пробелы данных, чтобы можно было продолжать диалог и разбирать, какие агенты и инструменты участвовали в ответе.

## AI-агенты и их возможности

Сильная часть проекта — не один общий AI-чат, а сеть специализированных агентов с контролируемыми зонами ответственности.

- **Domain Router Orchestrator** определяет, к какому специалисту отправить запрос, учитывает продолжения диалога из памяти и не отвечает общими советами, когда нужен фактический анализ.
- **Sales Agent** анализирует продажи, заказы, выручку, отмены, выкупы, воронку карточки, вклад артикулов, регионов и складов.
- **Marketing Agent** анализирует рекламные кампании, расходы, показы, клики, CPC, CTR, конверсию клика в заказ, ДРР, ставки, поисковые запросы, видимость и среднюю позицию.
- **Price Agent** анализирует регулярную цену, промо-цену, скидки, конкурентные цены, медиану рынка, долю конкурентов дешевле/дороже и ценовой сегмент.
- **Supply Agent** анализирует остатки, доступный запас, покрытие в днях, дефицит, out-of-stock, overstock, дозаказ, поставки, товары в пути и готовность к продаже.
- **Finance Agent** анализирует выручку, выплаты, комиссии, эквайринг, логистику, хранение, штрафы, удержания, закупочную себестоимость, маржу и прибыльность по SKU.
- **Diagnostic Orchestrator** собирает результаты доменных агентов в один бизнес-ответ, отделяет подтвержденные причины от неподтвержденных и формирует понятные действия.

Агенты работают через инструменты данных, а не через свободные догадки. Каждый доменный агент возвращает структурированный результат: summary, таблицы, findings, evidence, confidence, driver_class, recommendations, data_gaps и cross_agent_requests. Если агент видит фактор вне своей зоны, он не делает вывод сам, а создает узкий запрос к другому агенту.

В системе есть guardrails и tool policy: агентам задаются обязательные инструменты, проверяется наличие таблиц и evidence, запрещается показывать пользователю технические `nm_id` там, где нужен артикул/SKU, а рискованные рекомендации валидируются перед выдачей.

## Агентские раунды и память

Память системы разделена на два уровня: диалоговую память и память выполнения агентского workflow.

- **Диалоговая память:** `chat_sessions`, `chat_messages` и `chat_summaries` хранят историю чата, последние сообщения и краткое summary. Благодаря этому система понимает продолжения вроде "да", "сделай", "покажи" и не теряет контекст предыдущего ответа.
- **Память задач:** `agent_action_tasks` и `chat_selected_action_tasks` сохраняют задачи, извлеченные из findings и финального раздела "Что делать".
- **Память запусков:** `agent_run_traces` хранит статус запуска, primary agent, events и summary. Через API можно посмотреть список запусков и детали конкретного ответа.
- **Память раундов:** `agent_run_rounds`, `agent_run_questions`, `agent_run_responses` и `agent_run_gaps` фиксируют, какие проверки были запланированы, каким агентам заданы вопросы, какие ответы получены и какие пробелы данных остались открытыми.

Типовая логика раундов:

1. **Round 0, primary:** выбирается основной агент по intent пользователя и получает исходный вопрос.
2. **Round 1, cross-check:** строится план смежных проверок. Например, вопрос о продажах может отправить дополнительные проверки в supply и marketing.
3. **Round 2, follow-up/action safety:** выполняются follow-up запросы и проверки безопасности действий: снижение цены, масштабирование рекламы, дозаказ или распродажа.
4. **Round 3, gap resolution:** система пытается закрыть blocking gaps, если по SKU или метрике остались неподтвержденные или пустые зоны.
5. **Round 4, synthesis:** Diagnostic Orchestrator собирает финальный ответ: механика изменения, причины, матрица подтверждений, ограничения и действия.

Ограничения раундов заданы явно: до 5 смежных проверок в первом раунде, до 5 follow-up проверок во втором, до 3 попыток закрыть gaps и до 8 общих follow-up доменных вызовов. Это защищает систему от бесконечного анализа и держит ответ управляемым.

## ETL-процесс и слой данных

Проект опирается на PostgreSQL как центральное хранилище данных маркетплейса. Внешний контур загрузки кладет данные WB в доменные схемы, Airflow управляет регулярными и ручными пайплайнами, а этот репозиторий фиксирует backend, SQL-слой трансформаций и инструменты, через которые агенты читают данные.

Основной поток данных:

1. **Extract:** Airflow и парсеры загружают данные WB в PostgreSQL: продажи и заказы, воронку карточек, остатки и поставки, рекламные кампании, поисковые запросы, цены, конкурентов и финансовые отчеты.
2. **Transform:** SQL-слой нормализует данные, приводит разные источники к единой логике SKU, периода и домена анализа.
3. **Enrich:** дополнительные пайплайны добавляют расчетные признаки: себестоимость, конкурентное окружение, SEO-ключи, ценовые сигналы, релевантность конкурентов и визуальное сходство товаров.
4. **Orchestrate:** Airflow фиксирует порядок шагов, статусы, логи и ограничения параллельности. Для тяжелого анализа конкурентов используется разнос ответственности: контейнерный Airflow ставит задачу, а host-worker с браузерным окружением выполняет сбор.
5. **Serve:** backend дает read-only функции и готовые отчеты для агентов по финансам, продажам, маркетингу, ценам и остаткам.
6. **Analyze:** агенты вызывают только разрешенные tools, получают структурированные данные и превращают их в диагностические выводы.

Отдельный Airflow-пайплайн закрывает контур ценового AI-анализа. Он строит snapshot SKU, обновляет цены по ссылкам, готовит активные SKU, генерирует SEO-ключи, собирает конкурентов, нормализует их признаки, применяет hard filters, оценивает релевантность через LLM, проверяет визуальное сходство через Vision и собирает итоговую строку анализа по каждому SKU. Это усиливает Price Agent: он получает не только цену товара, но и контекст рынка, качества аналогов и уверенность в том, что конкурент действительно сопоставим.

ETL-слой считает и нормализует метрики, которые важны для работы с МП: продажи и выручку, заказы и отмены, конверсии воронки, рекламные расходы, CTR/CPC/ДРР, покрытие запасом, риск out-of-stock, комиссии, эквайринг, логистику, хранение, штрафы, выплаты, COGS и маржинальность там, где есть себестоимость.

## Ценовой AI-анализ и импорт данных

Ключевой parser-контур проекта — ценовой AI-анализ. Его бизнес-смысл — собрать по каждому активному SKU конкурентное окружение WB, проверить качество аналогов и подготовить данные для Price Agent.

- **Подготовка SKU:** pipeline берет активные товары, обновляет базовые данные и цены по ссылкам, формирует payload по каждому SKU и готовит его к конкурентному анализу.
- **Генерация поисковых ключей:** для каждого SKU создаются SEO/search keywords, по которым дальше ищутся потенциальные конкуренты на WB.
- **Сбор конкурентов WB:** parser собирает кандидатов по каждому SKU: товары-конкуренты, цены, признаки карточки и данные, нужные для сравнения с исходным товаром.
- **Host-worker для браузерного сбора:** тяжелая часть competitor search вынесена из контейнерного Airflow в отдельный host-worker с браузерным окружением. Airflow ставит задачу, ждет результат и продолжает pipeline после завершения сбора.
- **Нормализация признаков:** собранные товары приводятся к единой структуре: категория, характеристики, размеры, материал, цена, визуальные признаки и другие параметры, по которым можно сравнивать аналоги.
- **Отбор нерелевантных товаров:** pipeline применяет жесткие правила фильтрации, чтобы убрать случайные товары, нерелевантные категории и слабые аналоги до передачи в AI-оценку.
- **LLM relevance:** языковая модель оценивает, насколько кандидат действительно похож на исходный товар и может ли использоваться как конкурент для ценового анализа.
- **Vision-проверка аналогов:** для shortlist конкурентов используется визуальная проверка, чтобы отличать настоящие аналоги от товаров, которые похожи только по тексту или ключевым словам.
- **Финальная строка анализа:** pipeline собирает итог по SKU: конкурентный диапазон, релевантные аналоги, ценовой контекст, сигналы завышенной/заниженной цены и ограничения данных.
- **Связка с Price Agent:** Price Agent использует результат parser-контура не как сырой список конкурентов, а как предварительно очищенный, проверенный и объяснимый источник для ценовой диагностики.

Импорт себестоимости остается поддерживающим финансовым контуром: backend принимает Excel-файлы, валидирует артикулы и закупочную стоимость, сохраняет данные в финансовый слой и позволяет связывать ценовые рекомендации не только с рынком, но и с реальной маржинальностью SKU.

## Экономический эффект и экономия времени

Главный эффект системы — сокращение цикла от вопроса до действия: вместо ручного анализа в нескольких отчетах команда получает единый AI-ответ с подтверждениями, рисками, ограничениями данных и задачами для дальнейшей работы.

- **Сокращение времени диагностики:** вместо ручной сверки отчетов WB по продажам, рекламе, ценам, остаткам и финансам система собирает картину в одном AI-диалоге и показывает вероятные причины изменений.
- **Быстрее управленческие решения:** команда быстрее понимает, что делать с товаром: менять цену, проверять рекламу, пополнять остатки, останавливать слабую кампанию или пересчитывать маржу.
- **Снижение потерь от неверных действий:** рискованные рекомендации проходят дополнительные проверки. Это снижает вероятность уронить маржу скидкой, масштабировать неэффективную рекламу, дозаказать товар без спроса или допустить out-of-stock.
- **Экономия времени аналитиков и менеджеров:** AI берет на себя первичный анализ, сводку данных, поиск аномалий, сравнение доменов и подготовку задач, освобождая команду от ручной рутины.
- **Фокус на прибыльности, а не только на выручке:** система связывает продажи, рекламу, комиссии, логистику, хранение, себестоимость и маржу, чтобы решения принимались по реальной экономике SKU.
- **Быстрое выявление проблемных SKU:** система помогает находить товары с падением продаж, слабой рекламой, завышенной или заниженной ценой, риском дефицита, избытком остатков или ухудшением маржинальности.
- **Повышение отдачи от рекламы:** рекламные расходы анализируются вместе с продажами, конверсией, ценой, остатками и маржой, чтобы не оптимизировать кампании в отрыве от экономики товара.
- **Снижение риска stock-out и overstock:** агент по остаткам помогает видеть покрытие, дефицит, избыток, потребность в дозаказе и риск заморозки денег в складе.
- **Превращение аналитики в задачи:** выводы AI превращаются в конкретные действия для команды: проверить остатки, пересчитать цену, остановить слабую рекламу, сверить маржу, проверить поставку или обновить себестоимость.
- **Прозрачность экономического вывода:** система показывает, какие факторы подтверждены данными, где есть гипотезы и каких данных не хватает, чтобы не принимать решения на ощущениях.

## Работа с заказчиком и внедрение

Проект развивается в связке с бизнес-заказчиком и командой внедрения. В рабочем процессе участвуют product manager, крупное агентство, генеральный директор со стороны бизнеса и менеджер, который тестирует систему на реальных сценариях маркетплейса.

- **Сбор требований:** обсуждаются бизнес-задачи, боли команды, сценарии использования, нужные метрики, роли пользователей и ожидаемый формат AI-ответов.
- **Встречи и синхронизации:** проводятся регулярные созвоны по статусу разработки, качеству ответов агентов, UI, ETL, парсерам, финансовой логике и облачной инфраструктуре.
- **Согласование логики продукта:** отдельно согласуются агентские роли, структура финального ответа, правила безопасных рекомендаций, action tasks, память диалогов и формат диагностических выводов.
- **Презентации и демо:** система демонстрируется заказчику на реальных данных WB: чат, Web UI, агентские ответы, задачи, юнит-экономика, price AI analysis и результаты ETL.
- **Тестирование с бизнес-пользователем:** менеджер со стороны заказчика проверяет систему на практических вопросах, фиксирует неудобные места, неясные ответы, недостающие метрики и сценарии, которые нужно доработать.
- **Итерационные доработки:** обратная связь превращается в изменения backend, Web UI, промптов агентов, SQL-слоя, парсеров, Airflow DAG, action tasks и правил проверки выводов.
- **Объяснение работы системы:** заказчику объясняется, как устроены AI-агенты, почему система задает смежные проверки, где берутся данные, как читать confidence/evidence, что означают gaps и почему некоторые рекомендации требуют дополнительной проверки.
- **Управление ожиданиями:** отдельно проговариваются ограничения данных, зоны ответственности AI, различие между подтвержденной причиной и гипотезой, а также условия, при которых вывод можно считать безопасным для бизнес-действия.

## Что покрыто тестами

- Backend-контракты: работоспособность сервиса, чат, история, трассировки, SKU previews, финансовые отчеты и action tasks.
- Routing: корректное определение finance, marketing, sales, price и supply intent.
- Multi-agent workflow: основной агент, смежные агенты, второй раунд safety-checks и обработка guardrail failures.
- DB tools: readonly SQL validation, финансовые отчеты, SKU profit change и dashboard KPIs.
- Feature-модули: импорт себестоимости, action task extraction, unit economics и commission calculator.

## Технологический стек

## Облачная инфраструктура

Проект развернут в Yandex Cloud и использует managed-инфраструктуру для production-like работы AI-ECOM. Облачный слой закрывает полный цикл: загрузка данных WB, хранение в PostgreSQL, обработка через ETL, запуск AI-агентов, выдача результата через backend и Web UI.

- **Yandex Managed Service for Apache Airflow:** оркестрация ETL-процессов, запуск DAG, парсеров WB, пересчетов аналитического слоя и price AI analysis.
- **Yandex Managed Service for PostgreSQL:** центральное хранилище данных маркетплейса, результатов ETL, аналитического слоя и данных для AI-агентов.
- **Yandex Compute Cloud:** отдельные виртуальные машины для backend/API, Web UI/Nginx, worker-процессов, фоновых agent runs и browser-based parser задач.
- **Docker / Docker Compose:** упаковка backend, worker, UI, Redis и вспомогательных сервисов в воспроизводимые контейнеры.
- **Nginx:** отдача Web UI и reverse proxy к backend/API и Task UI.
- **Airflow + Compute workers:** разделение оркестрации и тяжелых задач: Airflow управляет пайплайном, а compute-воркеры выполняют backend, AI-задачи, парсеры и браузерный сбор конкурентов.

Текущая инфраструктурная схема включает managed Airflow-кластер, managed PostgreSQL-кластер и три виртуальные машины Compute Cloud. Такая конфигурация отделяет хранение данных, управление ETL и вычислительный слой, а также позволяет масштабировать backend, UI, worker и parser-нагрузку независимо.

## Безопасность и доступы

Система проектируется так, чтобы AI-агенты работали с данными контролируемо и не получали лишних прав на production-инфраструктуру.

- **Разделение данных:** аналитическая база WB и база памяти чатов/агентских запусков разделены логически и конфигурационно.
- **Read-only доступ для агентов:** аналитические агенты получают данные через разрешенные backend tools и SQL-инструменты, а не через свободный доступ к базе.
- **Контроль источников:** каждый доменный агент работает только с разрешенными источниками и не должен делать выводы по метрикам, которых нет в его зоне данных.
- **Secrets management:** OpenAI API keys, PostgreSQL credentials, Redis URL, Airflow credentials и production `.env` не хранятся в коде.
- **Ключи по фичам:** под каждую AI-фичу используется отдельный API key, что позволяет разделять доступы, ограничивать blast radius и мониторить затраты по конкретным сценариям.
- **Безопасные рекомендации:** рискованные действия вроде снижения цены, масштабирования рекламы, дозаказа или распродажи проходят дополнительные проверки по смежным доменам.
- **Разделение сред:** локальная разработка, Docker runtime и облачный production-контур используют отдельные настройки окружения.

## Масштабирование, надежность и мониторинг затрат

Архитектура разделяет нагрузку по слоям, чтобы можно было независимо масштабировать UI, backend, worker-процессы, ETL и parser-задачи.

- **Backend / worker split:** backend отвечает за API и WebSocket, а отдельный worker выполняет долгие agent runs и фоновые задачи через Redis/RQ.
- **Managed services:** PostgreSQL и Airflow вынесены в managed-сервисы Yandex Cloud, что снижает операционную нагрузку и дает отдельный слой надежности для хранения данных и ETL.
- **Compute separation:** три виртуальные машины Compute Cloud позволяют разделить backend/API, UI/Nginx и тяжелые worker/parser задачи.
- **Healthchecks:** backend, Redis, PostgreSQL memory DB и Airflow-сервисы проверяются через healthcheck/smoke-check сценарии.
- **Airflow observability:** Airflow хранит статусы DAG, логи задач, ошибки импорта и историю запусков ETL/parser pipeline.
- **Agent observability:** agent traces, rounds, questions, responses и gaps показывают, какие агенты вызывались, какие проверки выполнялись и где были ограничения данных.
- **Cost monitoring:** отдельные OpenAI API keys под разные фичи позволяют отслеживать расход по направлениям: чат, агентский анализ, память, price AI analysis, LLM relevance, Vision-проверки и другие AI-сценарии.
- **Контроль дорогих операций:** тяжелые AI/LLM/Vision и browser-parser этапы выделены в отдельные pipeline-части, что позволяет отслеживать их стоимость, частоту запуска и бизнес-эффект.
- **Rollback:** при ошибке healthcheck инфраструктура откатывается на предыдущий image/tag или compose release.

## Сбор логов и наблюдаемость

В проекте предусмотрен сбор и анализ логов на нескольких уровнях: backend, worker, Airflow, parser pipeline, AI-агенты и облачная инфраструктура. Это позволяет разбирать ошибки, контролировать качество ответов AI и понимать, на каком этапе возникла проблема: загрузка данных, ETL, база, агентский анализ, Web UI или внешний API.

- **Backend logs:** фиксируются запросы к API, ошибки сервисов, проблемы WebSocket-чата, статусы agent runs и обращения к инструментам данных.
- **Worker logs:** отдельные фоновые процессы логируют выполнение долгих agent runs, очереди Redis/RQ, таймауты и ошибки обработки задач.
- **Airflow logs:** каждый DAG и task сохраняет историю запусков, статусы, retries, import errors и stack traces по ETL/parser-процессам.
- **Parser logs:** price AI parser логирует этапы сбора конкурентов, host-worker задачи, ошибки браузерного сбора, нормализацию, фильтры, LLM relevance и Vision-проверки.
- **Agent traces:** система хранит, какой агент был основным, какие смежные проверки запускались, какие вопросы задавались, какие ответы получены и где остались пробелы данных.
- **Infrastructure logs:** Docker/Compose, Nginx, PostgreSQL, Redis и Yandex Cloud помогают контролировать доступность сервисов, сетевые ошибки и состояние runtime.
- **Разбор инцидентов:** по логам можно восстановить цепочку от пользовательского вопроса до финального AI-ответа и понять, была ли проблема в данных, ETL, инструменте, агенте или UI.

Сбор логов нужен не только для технической отладки, но и для качества AI: по traces и логам видно, где агент сделал лишний вывод, где не хватило данных, где нужно улучшить prompt, tool или ETL-слой.

## CI/CD пайплайн и работа с GitHub

В проекте используется воспроизводимый CI/CD-контур на базе GitHub, Docker и Docker Compose. Репозиторий содержит Dockerfile для backend, compose-конфигурацию сервисов, healthcheck backend-сервиса, отдельные сервисы backend/worker/PostgreSQL memory/Redis и правило деплоя через Docker/uvicorn.

Схема работы с GitHub:

1. **Branch workflow:** разработка идет в feature-ветках, изменения попадают в основную ветку через Pull Request.
2. **Pull Request review:** в PR проверяются изменения backend, Web UI, SQL-слоя, Airflow DAG и parser-логики; отдельно смотрятся риски для агентского workflow и данных.
3. **Secrets management:** OpenAI keys, PostgreSQL credentials, Redis URL, Airflow credentials и production `.env` не коммитятся, а хранятся в GitHub Secrets или в окружении сервера.
4. **No generated artifacts:** локальные build/dist артефакты исключены из репозитория и деплоя, чтобы production всегда запускал актуальный runtime-код.

CI pipeline:

1. **Backend checks:** установка Python-зависимостей, import-check FastAPI приложения, проверка конфигурации, запуск unit/API тестов, smoke-check health endpoint.
2. **Agent checks:** тесты routing, multi-agent workflow, guardrail failures, action task extraction, readonly SQL validation и доменных tools.
3. **Frontend checks:** `npm ci`, TypeScript build, Vite build для Web UI и Task UI.
4. **Docker checks:** сборка backend image, сборка Web UI/Task UI image, проверка `docker compose config`, smoke-запуск backend с healthcheck.
5. **Airflow checks:** проверка импорта DAG, отсутствие import errors, smoke-запуск parser-модулей без реального production side effect.
6. **Security / hygiene:** проверка отсутствия секретов в diff, запрет коммита локальных binary/build артефактов, контроль `.env` и generated files.

CD pipeline:

1. **Build:** собираются Docker images для backend, worker, Web UI и Task UI.
2. **Deploy:** сервисы обновляются через Docker Compose: backend, worker, Redis, PostgreSQL memory DB, UI/Nginx; Airflow-контур деплоится отдельно через свой compose-файл.
3. **Migrations / init:** применяется init SQL для memory DB и необходимые SQL-скрипты перед включением agent workflow.
4. **Healthcheck:** проверяется backend health, доступность Web UI, Redis, memory Postgres и Airflow scheduler/webserver.
5. **Rollback:** при ошибке healthcheck выполняется откат на предыдущий image/tag или предыдущий compose release.

## План развития системы

Следующий этап развития AI-ECOM — переход от диагностической AI-аналитики к системе управления рекомендациями и измерения экономического эффекта. Цель развития — замкнуть цикл от AI-вывода до измеримого бизнес-результата.

- **Прогноз эффекта до действия:** система будет оценивать ожидаемый результат рекомендации до ее выполнения: влияние на продажи, маржу, рекламные расходы, остатки, риск out-of-stock и cash-flow.
- **Контроль выполнения рекомендаций:** action tasks будут отслеживаться как управленческие задачи: кто взял в работу, что выполнено, что отложено, что проигнорировано и почему.
- **Оценка фактического результата:** после выполнения рекомендации система будет сравнивать прогноз с фактом: изменились ли продажи, маржа, ДРР, остатки, цена, рекламная эффективность или прибыльность SKU.
- **Анализ невыполненных рекомендаций:** система будет фиксировать, какие рекомендации не были выполнены, и оценивать возможные потери или упущенный эффект по сравнению с прогнозом.
- **Feedback loop для AI-агентов:** результаты выполненных и невыполненных рекомендаций будут возвращаться в контур анализа, чтобы улучшать правила, prompts, confidence и приоритизацию будущих действий.
- **Приоритизация действий по экономике:** рекомендации будут сортироваться не только по срочности, но и по ожидаемому экономическому эффекту, риску и сложности выполнения.
- **Контроль ответственности:** система сможет связывать рекомендации с исполнителями, сроками и статусами, превращая AI-аналитику в управляемый операционный процесс.
- **Выполнение операционных задач:** следующий уровень системы — не только рекомендовать действие, но и выполнять его после подтверждения пользователя: изменить цену, создать рекламную кампанию, запустить промо, пересчитать поставку, создать заявку на поставку, обновить себестоимость или поставить задачу ответственному менеджеру.
- **Human-in-the-loop управление:** рискованные операции будут выполняться только через подтверждение, лимиты, журнал действий и проверку условий безопасности, чтобы AI не менял коммерческие параметры без контроля человека.
- **Интеграции с учетными и CRM-системами:** система сможет подключаться к МойСклад, CRM и внутренним операционным системам, чтобы синхронизировать товары, остатки, поставки, задачи, статусы клиентов, сделки и управленческие действия.
- **Операционный контур маркетплейса:** AI-ECOM сможет связывать аналитику, рекомендации и исполнение в один процесс: обнаружить проблему, оценить экономический эффект, предложить действие, выполнить операцию через интеграцию и затем измерить фактический результат.
